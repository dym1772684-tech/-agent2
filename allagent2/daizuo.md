下面按“智能体从接收需求到完成任务”的完整链路，给你一份设计文档。以下都是建议方案，不代表你的项目已经实现；不再查看代码，也不修改代码。

1．整体链路应该怎么设计

建议把系统分成两条链路：

在线执行链路：处理当前用户请求。

后台治理链路：负责知识入库、长期记忆整理、评估、监控和成本分析。

在线执行顺序：

text
用户输入
  ↓
身份识别、权限范围、请求校验
  ↓
意图识别、复杂度评估、信息是否充足
  ↓
直接回答 / 检索问答 / 数据分析 / 多步骤任务
  ↓
生成计划，明确依赖和验收标准
  ↓
为当前步骤选择 Skill、工具、模型
  ↓
召回相关记忆和知识，组装上下文
  ↓
模型回答，或者提出工具调用
  ↓
参数校验 → 权限检查 → 执行工具
  ↓
结果校验、错误处理、更新 State
  ↓
判断：继续执行 / 调整计划 / 等待用户 / 结束
  ↓
验收结果、输出答案和证据
  ↓
保存检查点、记录费用、筛选长期记忆
关键原则：模型负责提出判断和行动，程序负责约束、执行、记录和验收。

不要把权限检查、费用上限、重试次数等硬约束只写在提示词里。

2．用户输入后，怎么识别意图

不要只给请求贴一个“问答”“写代码”的标签。应该提取一个结构化的任务说明：

json
{
  "intent": "data_analysis",
  "goal": "找出销售额下降最多的三个区域",
  "inputs": ["sales.xlsx"],
  "deliverables": ["分析结论", "统计表"],
  "constraints": ["不能修改原始文件"],
  "requires_retrieval": false,
  "requires_tools": true,
  "missing_information": ["对比时间范围"],
  "risk_level": "low"
}
建议采用三层识别：

确定性规则：识别明确命令、附件类型、指定工具、禁止操作。

轻量模型分类：理解自然语言、提取目标和约束。

复杂任务升级分析：遇到多个目标、模糊表达、复杂依赖时，交给能力更强的模型。

是否追问，看缺失信息会不会改变结果：

“分析最近三个月销售额”，数据中时间明确，可以继续。

“删除没用的数据”，删除范围不明确，需要先澄清。

次要格式偏好不明确，可以采用默认值并说明。

模型给出的置信度只能作为信号，不能当作可靠概率。应该用标注样本评估分类准确率和追问是否合理。

3．任务怎么拆解，谁先谁后

把任务拆成一个有向无环图 DAG，而不是一串模糊的待办事项。

例如：

text
读取数据结构
      ↓
检查字段与数据质量
      ↓
确定统计口径
      ↓
计算各区域指标
      ↓
校验计算结果
      ↓
生成结论和图表
每个子任务至少包含：

json
{
  "task_id": "t3",
  "goal": "计算各区域销售额同比",
  "depends_on": ["t2"],
  "input_refs": ["artifact://clean_sales"],
  "output_schema": "RegionGrowthResult",
  "acceptance_criteria": ["区域完整", "分母为零时单独标记"],
  "status": "pending",
  "max_attempts": 3
}
调度顺序由程序决定：

依赖全部满足，才允许执行。

没有依赖关系、不会争抢资源的任务，可以并行。

修改同一个文件、同一张表的任务，需要串行或加锁。

前置任务失败，依赖它的任务不能假装正常继续。

不存在的依赖 ID、循环依赖，必须在执行前拒绝。

任务拆解不意味着必须创建多个智能体。大多数任务用一个调度器配合不同功能节点就能完成；只有独立调查、交叉审查等场景才值得引入多智能体。

4．工具调用顺序怎么确定

工具顺序来自数据依赖和风险约束。

典型顺序：

text
先查元信息
→ 再定位目标
→ 再读取必要内容
→ 再计算或生成修改方案
→ 检查权限
→ 执行操作
→ 校验实际结果
例如修改代码：

text
列出相关文件 → 搜索符号 → 读取函数 → 分析依赖
→ 生成补丁 → 应用补丁 → 运行相关检查
例如数据库分析：

text
获取可访问表结构 → 确定指标口径 → 生成查询
→ SQL校验 → 只读执行 → 检查结果 → 解释
每一步可以由模型选择工具，但执行器必须检查：

工具是否在当前任务的允许列表中。

参数是否满足 Schema。

目标资源是否在授权范围内。

当前预算是否允许执行。

是否需要审批。

是否已经执行过相同的有副作用操作。

5．不同任务怎么选择不同模型

建立模型能力表，不要只按“哪个模型更贵”分配。

任务	建议选择依据
意图分类、格式转换	低延迟、结构化输出稳定
简单摘要、文本抽取	成本低、信息保留率高
复杂规划、跨文件推理	推理能力和长任务稳定性
代码生成与修复	代码基准和实际项目通过率
图片、扫描文档理解	多模态能力、OCR表现
Embedding	中文、领域语义、检索实测效果
Rerank	查询与文档相关性判断能力
路由可以分两步：

硬过滤：上下文容量、工具调用能力、数据合规、部署区域、可用性。

软排序：质量、延迟、预计成本、当前负载。

建议采用“先满足任务需求，再控制成本”的策略：

简单任务使用轻量模型。

Schema 校验反复失败、证据整合困难、任务复杂度增加时升级。

高风险结果需要独立验证，不能仅靠换更强模型。

切换模型后，重新计算上下文预算。

不要只根据输入长度判断复杂度；一句“定位并发死锁原因”可能比一万字摘要更难。

6．Skill 应该怎么设计

Skill 是“可复用的任务方法”，工具是“实际执行的能力”。

例如：

工具：执行 SQL。

Skill：销售分析的方法、指标口径、异常检查和报告要求。

一个 Skill 建议包含：

text
名称和版本
适用场景、不适用场景
输入要求
执行步骤
可用工具
权限要求
输出格式
验收标准
异常处理
示例和辅助资源
例如“销售分析 Skill”规定：

检查日期、金额、区域字段。

确认退款、币种、税费口径。

计算同比、环比。

处理缺失值和零分母。

输出指标表、结论、数据来源。

加载采用渐进方式：

平时只保留 Skill 名称和简介。

选中后加载执行说明。

需要时再读取示例、脚本、参考资料。

不要每次把所有 Skill 全量塞进上下文。Skill 也不能授予超出用户和系统允许范围的权限。

7．短期记忆和长期记忆怎么区分

建议区分四类信息：

类型	内容	生命周期
工作状态 State	当前计划、步骤状态、预算、待审批动作	当前任务及恢复期间
短期记忆	最近对话、当前任务摘要、临时发现	当前会话或任务
长期记忆	稳定偏好、确认事实、可复用经验	跨会话
知识库	文档、代码、业务资料、数据说明	随知识版本维护
几个容易混淆的点：

数据保存到磁盘，不代表它就是长期记忆。

聊天记录持久化，不代表下次都要放进上下文。

向量数据库只是存储和检索方式，不决定记忆类型。

上下文窗口只是本次模型调用能看到的信息。

8．什么时候写入短期记忆，什么时候进入长期记忆

短期记忆应当随任务执行持续更新：

用户新增要求。

已经完成的步骤。

关键工具结果及引用。

已发现的问题。

临时假设。

尚未完成的事项。

长期记忆不要直接保存模型想到的内容。建议走以下流程：

text
提取候选记忆
→ 判断是否有跨会话价值
→ 核验来源
→ 检查敏感性和保存权限
→ 去重、检测冲突
→ 写入并建立索引
适合进入长期记忆：

用户明确要求记住的稳定偏好。

经确认的项目约束和业务定义。

多次验证有效的工作方法。

已完成事件的简要事实记录。

不适合直接进入长期记忆：

一次性的临时指令。

未验证的推断。

工具错误输出。

密钥、密码、访问令牌。

外部文档中要求智能体改变行为的指令。

建议每条长期记忆有：

text
memory_id、user_id、project_id、type、content
source_ref、created_at、updated_at、expires_at
confidence、sensitivity、status、supersedes
发生冲突时保留来源和版本。例如用户原来偏好 Python，后来明确改成 TypeScript，应更新当前偏好，同时保留可追溯关系。

9．Context Manager 到底负责什么

Context Manager 的职责是：为每一次模型调用，选择并组织足够完成当前步骤的信息。

它不是简单的“聊天记录拼接器”。

输入包括：

当前任务和子任务。

模型上下文容量。

系统约束。

Skill。

历史摘要和最近对话。

检索证据。

工具结果。

预算和权限信息。

输出是经过预算检查的模型请求。

建议组装顺序：

text
系统规则
→ 当前任务目标和硬约束
→ 当前步骤说明
→ 必要 Skill 和工具 Schema
→ 关键事实与任务摘要
→ 相关证据
→ 最近对话
具体能力包括：

Token 预算分配。

相关性筛选。

去重。

摘要和裁剪。

工具调用与工具结果配对。

来源标记。

敏感信息过滤。

模型切换后的重新适配。

外部检索内容应标记为证据数据，不能因为被放进上下文就获得系统指令的权限。

10．上下文窗口怎么限定和计算

首先从模型配置中读取实际容量，不能全局写死一个窗口值。

基本约束：

text
输入 Token
+ 预留输出 Token
+ 安全余量
≤ 模型上下文上限
同时还要遵守模型单独的最大输出限制。不同服务商对推理 Token、隐藏开销的处理可能不同，预算必须按实际接口规则计算。

输入 Token 包含：

text
系统提示词
+ Skill
+ 工具定义
+ 用户输入
+ 历史消息
+ 记忆摘要
+ RAG证据
+ 工具结果
+ 消息格式开销
假设某模型上下文上限为 128,000 Token：

预留输出 8,000。

安全余量 4,000。

输入最多 116,000。

这只是容量上限，不是每次都要用满。大量低相关信息会增加费用，也可能降低效果。

历史消息条数只能作为辅助限制，因为一条工具输出就可能占几万 Token。

11．什么时候触发压缩，压缩后怎么保留重要信息

建议设置两个机制：

提前压缩：预计下一次调用接近输入预算，例如达到 75%～85%。

发送前硬检查：无论是否压缩过，最终请求都必须符合上限。

这些比例是可调初始值，应通过实际数据确定。

压缩顺序建议：

删除重复证据和无关消息。

把巨大工具输出保存为外部产物，只保留摘要和引用。

缩小检索片段。

摘要较旧的对话和已完成步骤。

保留最近必要交互。

摘要采用固定结构：

text
当前目标
用户硬约束
已确认事实及来源
已做出的决策
已完成步骤及结果引用
未完成步骤
错误与已尝试的修复
待确认事项
下一步
应当单独保存、避免被摘要改写的信息：

授权范围。

禁止操作。

金额、时间、文件路径、任务 ID 等关键值。

验收标准。

待执行动作的准确参数。

压缩是有损操作，不能承诺百分之百不丢信息。降低风险的方法是：

原始记录可检索。

关键字段结构化保存。

摘要保留来源引用。

压缩后自动检查硬约束、待办和关键值是否仍在。

避免反复对旧摘要继续摘要，必要时从原始记录重建。

12．Token 怎么计数

分为调用前估算和调用后记账。

调用前：

使用对应模型或服务商支持的 tokenizer、计数接口。

统计完整请求，包括工具 Schema 和消息格式。

图片、音频等按服务商的计量规则估算。

无法精确计数时使用保守估计和安全余量。

不要把“一个汉字等于一个 Token”当固定规则。

调用后：

记录服务端返回的 usage。

区分输入、缓存输入、输出，以及服务商单独报告的其他项目。

记录 request_id、model、task_id、step_id、attempt。

累计 Token 和上下文 Token 是两个概念：

上下文 Token：某一次请求占用了多少窗口。

累计 Token：整个任务的所有调用总消耗。

同一段历史发送十次，可能被计入十次输入；命中缓存时，计费方式另按服务商规则处理。

13．费用怎么计算

模型费用的一般形式：

text
单次费用 =
非缓存输入Token × 输入单价
+ 缓存输入Token × 缓存单价
+ 输出Token × 输出单价
+ 其他独立计费项目
单价如果按每百万 Token 给出，上式对应项需要除以 1,000,000。

注意：

某些 usage 中的缓存 Token 是输入 Token 的子集，不能重复相加。

推理 Token 如果已包含在输出计费里，不要再次收费。

具体项目按服务商实际账单口径归一化。

总任务成本还应包括：

所有模型调用和重试。

Embedding。

Rerank。

搜索、OCR 等付费工具。

数据库查询、计算资源、存储等成本。

维护带生效日期的价格表，记录模型版本、币种和计费单位。任务开始前估算预算，每一步执行前检查剩余额度；实际费用最终与服务商账单核对。

14．RAG 的完整步骤是什么

RAG 分为入库和查询两部分。

入库：

text
接收文件
→ 格式解析/OCR
→ 清洗和去重
→ 保留标题、段落、表格等结构
→ 切分 Chunk
→ 添加来源、权限和版本元数据
→ 生成 Embedding
→ 写入向量索引
→ 写入关键词索引
→ 校验入库完整性
查询：

text
理解问题
→ 确定可访问知识范围
→ 必要时拆分或改写查询
→ 向量检索与关键词检索
→ 合并候选
→ Rerank
→ 去重、必要时补充相邻内容
→ 根据Token预算选证据
→ 模型生成答案
→ 检查引用与结论是否匹配
Chunk 至少保存：

text
document_id、chunk_id、content、source_ref
title_path、page_or_line、version
tenant_id、acl、embedding_version
权限过滤应进入检索过程，未经授权的内容不能进入模型上下文；重排和缓存也必须遵守同一权限边界。

15．怎么提高 RAG 精确性

先按问题类型选择检索方式：

问题类型	优先方式
错误码、订单号、函数名	精确匹配、关键词检索
概念性问答	向量检索
同时含术语和自然语言	混合检索
总额、排名、同比	SQL或计算引擎
代码调用关系	符号索引、AST、引用关系
具体改进：

先提高解析质量：表格列错位、标题丢失，后续算法难以补救。

按结构切分：文档按章节，代码按函数，表格按业务单元。

给片段补充必要背景：例如章节标题、表名、字段说明。

混合召回：BM25 补精确词匹配，向量检索补语义匹配。

使用 Rerank：从几十条候选中挑选少量真正有用的证据。

处理版本和时效：避免旧规定覆盖新规定。

控制重复和证据覆盖：不能前五条都是同一段内容的变体。

允许“证据不足”：不要强行拼出答案。

不同检索器的原始分数通常不在同一尺度上，不宜直接相加。可以使用排名融合方法，例如 RRF，或者经过校准后再做加权融合。

Top-K、Chunk 大小、重叠长度，都应该根据评估集调参，而不是使用一个固定数字覆盖全部资料。

16．RAG 怎么评估

建立一批有代表性的问题，并标注：

正确答案或判定标准。

应命中的文档、片段或数据记录。

时间和版本要求。

用户权限。

无法回答的情况。

分层评估：

层面	指标
解析入库	内容完整率、表格还原准确率、失败率
检索	Recall@K、Precision@K、MRR、nDCG
生成	正确性、证据支持度、完整性
引用	引用准确率、引用覆盖率
无答案	正确拒答率、误拒答率
安全	越权检索和信息泄漏率
性能	P50/P95延迟、单次成本
例如：

text
Recall@K =
前K条结果中命中的相关证据数
÷ 标注的相关证据总数
人工标注可能不完整，所以指标需要结合样本复核。

评估时分别定位：

证据根本没召回。

召回了，但被重排淘汰。

选中了，但上下文裁剪丢掉。

证据都在，模型仍回答错误。

这比只看一个“最终回答评分”更有用。

17．百万行 Excel 怎么处理，怎么入库

首先分清需求：

“查询某条记录”。

“统计总额和排名”。

“理解文本备注”。

“对全部记录分类”。

这四类任务不应使用同一种处理方式。

百万行结构化数据，应优先进入分析数据库或列式文件；不要默认逐行向量化。

建议流程：

text
上传原始文件到对象存储
→ 创建异步导入任务
→ 流式读取
→ 校验表头和字段类型
