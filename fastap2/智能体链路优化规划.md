## 一、现状链路

```
POST /api/v1/agent/chat
  → ACL(agent:chat) + 限流(10次/分) + 敏感守卫 + thread 属主校验
  → run_in_threadpool(run_agent)
      → intent_plan          parser LLM → intent / query / next_need
      → route_by_intent      只看 intent
          ├─ weather / elder_profile / health_record → first_llm_call（不检索）
          ├─ knowledge                               → check_rag → first_llm_call
          └─ general                                 → final_output
      → first_llm_call ⇄ tool_use（最多 3 轮，网关鉴权 → 查库 → 脱敏）
      → final_output         parser LLM 再跑一次 → 结构化字段
  → get_state → answer（缺失时回退最后一条 AI 消息）
```

## 三、优化方案

### 阶段 A · 修正确性（1–2 天，收益最大，建议先做）

**A1 把 prompts 接进链路**
- `prompts.py` 导出 `system_prompts`，在 `bootstrap.run_agent` 构造初始 state 时作为 SystemMessage 注入，替换现在那句临时文案。
- 按 `user_role` 动态拼装（prompts.py 里已有 `dynamic_prompt` 雏形，可直接用）。
- 顺手修掉 prompts 里残留的旅游"工作流程"（行程规划/美食/景点/交通/住宿），改成养老流程。

**A2 知识库与业务对齐**
- 新建 `rag/elder_care.md`（养老养生知识：慢病饮食、老年运动、用药常识、季节养生、医保政策）。
- 保留旅游库做对照，或改成双 collection + metadata `{domain: "elder_care"|"travel"}`，检索按业务过滤。
- 每个 chunk 带 `{source, section, updated_at}` 元数据；rag 节点拼接时加 `[来源: xxx]` 前缀 → 兑现"标注来源、日期"要求。

**A3 接住结构化输出**
- `result = _state.agent.invoke(init_state, config=config)` 接收返回值，直接用 `result["answer"]`。
- 同时在 `state_schema` 补 `answer: Optional[str]`，让兜底链路也有确定字段。

**A4 新增 `ask_user` 分支**
- `route_by_intent` 增加：`next_need.kind == "user_input"` → `ask_user` 节点，返回追问文案 + `required_fields`，直接 END。
- 前端收到追问后带补充信息重入，靠 checkpointer 接续。

**A5 急救短路（规则优先，零 token）**
- 在 `intent_plan` 之前加 `emergency_guard` 节点：正则命中"胸痛/胸闷/说话不清/一侧无力/意识模糊/大量出血/呼吸困难" → 直接输出 120 建议 + 绑定老人信息 + 通知家属，跳过后续全部节点。
- 规则判定放在 LLM 之前，保证零延迟、零误判成本。

**A6 修 SystemMessage 堆积**
- 把"你需要调用工具…"与 `rag_context` 合并成一条系统消息，并加幂等判断。

### 阶段 B · 降本提效

**B1 parser 只跑一次**
- `intent_plan` 降级：先用规则/关键词匹配（"血压""血糖""天气""档案"），命中直接定 intent，不调 LLM；未命中才走 LLM。
- `final_output` 保留完整 `ParsedOutput` 调用。
- 预计省掉约一半的结构化调用开销。

**B2 消息裁剪**
- 把 `allagent2/middleware/trim_messages` 改写成 `StateGraph` 能用的前置函数，在 `first_llm_call` 入口对 messages 做窗口裁剪；超长部分压缩成一条 summary 塞回。

**B3 RAG 持久化 + 预构建**
- `EphemeralClient` → `PersistentClient(path="./rag/chroma_db")`。
- 离线脚本 `build_index.py` 预构建；embedding 模型也做成单例（rerank 已做）。
- 切块从 `split("\n\n")` 升级为 `RecursiveCharacterTextSplitter(chunk_size=500, overlap=80)`。

**B4 补齐真权限**
- 给 `plan`/`llm`/`summarize` 加实质校验（如 llm 节点校验 token 预算与模型白名单），或删掉空壳标签，避免"假安全感"。

**B5 修小 bug**
- `tool_results` 改为 list 追加；`max_tool_rounds` 透传进 configurable；embedding 降级时打 ERROR 日志并上报告警。

### 阶段 C · 体验

**C1 SSE 流式**
- 新增 `GET /api/v1/agent/chat/stream`，用 `astream(stream_mode=["messages","custom"])` 推 token + `phase` 事件。
- `dashboard.html` 已有 `agent/chat` 调用，改造成本低，体验提升最大。

**C2 持久化 checkpointer**
- `InMemorySaver` → SQLite/MySQL saver；配套 `conversation` / `message` 表落库（已有 `ConversationOwner`，可扩展）。

**C3 多轮摘要**
- 超过 N 轮把历史压缩成 summary 存入长期记忆，控制 context 增长。

### 阶段 D · 可观测与治理

- **D1** token 计数 + 每会话预算，超预算自动降级到便宜模型。
- **D2** 把 `/agent/trace` 的轨迹结构化落表（或接 Langfuse/LangSmith），支持按 thread 回放。
- **D3** 评测集：20–30 条黄金问答，指标 = 检索命中率 / 工具调用成功率 / 急救召回率 / 违规医嘱检出率。改版先跑回归。
- **D4** 长期记忆：LangGraph `Store` 存老人画像与偏好（慢病、忌口、运动耐受），每轮注入。

### 阶段 E · 还能加什么（能力扩展，按价值排序）

| 方向 | 具体内容 | 价值 |
|---|---|---|
| **verify 自校验节点** | final_output 后加校验节点：有没有编造档案里没有的数据？有没有越权内容？有没有违反"不诊断不开药"？不通过→回退重写一次 | 医疗场景最值得加的一道闸 |
| **健康趋势分析工具** | 对 `health_record` 做统计：7 天血压均值/趋势/波动，异常值标红 | 从"查记录"升级到"看趋势"，是养老业务的核心差异点 |
| **异常预警规则引擎** | 血压 > 140 连续 3 次 → 自动生成告警 + 通知家属 | 可落地的真实业务价值 |
| **多智能体拆分** | supervisor + 档案查询 / 健康分析 / 养生建议 / 安全审核 四个子 agent | 现在单图塞了所有职责，改一处影响全局 |
| **RAG 增强** | query 改写（"最近身体咋样" → "最新健康记录 血压 血糖"）、HyDE、按老人慢病标签做 metadata 过滤 | 检索准确率提升最直接 |
| **用药/复诊提醒工具** | 用药计划、复诊日历、相互作用提示（仅提醒，不替代医嘱） | 高频刚需 |
| **MCP 接入** | `mcp/` 目录目前是空的，用 `MultiServerMCPClient` 接入外部工具 | 工具扩展标准化 |
| **Human-in-the-loop** | 生成给家属的健康报告、用药提醒 → 人工确认后再发 | 高风险操作兜底 |

## 四、推荐执行顺序

```
第 1 步（半天）A1 + A2 + A3    人设接入 / 知识库换血 / 接住输出   ← 投入产出比最高
第 2 步（半天）A4 + A5 + A6    追问分支 / 急救短路 / 修堆积
第 3 步（1 天）B1 + B3          parser 去重 / RAG 持久化预构建
第 4 步（1 天）C1                SSE 流式（体验跃迁）
第 5 步（1 天）B5 + D1 + D3     小 bug / 成本统计 / 评测集
第 6 步（持续）E 系列            按业务价值挑着加
```

> 原则：**先让链路"想对"，再让它"想得快、想得省"**。
> 阶段 A 全部完成前，不建议动阶段 C/D —— 在错的链路上加流式，只会让错误答案更快地到达用户。
